# Решение: дедуп карточек медиа при нескольких пользователях

**Статус:** принято (вариант B — копии пер-юзер)
**Область:** `backend/media` (модель `MediaEntry`, `ImportView`, `MediaEntryViewSet`), частично `backend/okid/settings.py`

## Контекст

Модель `MediaEntry` хранит `user` и по одной копии медиа на каждого пользователя
(`backend/media/models.py:52`). Дубли одной и той же карточки в разрезе пользователей
это осознанный выбор: у каждого своя библиотека и свои поля (`my_status`, `my_rating`,
`download_status`, `is_favorite`), правки одного пользователя не затрагивают других.

Отдельно от этого есть настоящие **баги-дубли внутри одного пользователя**. Причины разные,
и не все они решаются одинаково.

## Что решает

| № | Сценарий дубля | Причина | Решается |
|---|---|---|---|
| 1 | Параллельный импорт одного `external_id` (двойной клик, две вкладки, retry) | TOCTOU: `ImportView._find_existing` затем create, без транзакции и DB-ограничения (`backend/media/views.py:931-977`); gunicorn в 3 воркера (`docker/backend.Dockerfile:19`) | **Да** |
| 2 | Импорт из Шикимори, потом из ПоискКино (тот же тайтл) | Внешние id из разных архивов не связаны, матч идёт по «pk **или** shikimori» | Нет (Фаза 2) |
| 3 | Ручное создание одинаковых записей | `MediaCreatePage` без дедупа | Нет (продуктовое решение) |
| 4 | Импорт без внешнего id дважды | См. `test_import_without_external_ids_not_deduplicated` | Нет (частный случай 3) |

Цель Фазы 1 — устранить сценарий 1 (самый вероятный и самый «незаметный»),
не меняя семантику пер-юзерных копий и не трогая фронтенд.

## Как решаем

### Фаза 1 — низкий риск, закрывает сценарий 1

1. **Миграция-чистка существующих дублей.** Перед созданием ограничений найти строки с
   одинаковым `(user, external_pk_id)` и `(user, external_shikimori_id)` (только непустые),
   слить: оставить самую старую, перенести `MediaHistory`, `MediaInformer`, `CollectionItem`,
   затем удалить лишние. Склейка по точному id, а не по названию — безопасна.

2. **Частичные уникальные ограничения** на `MediaEntry`:

   - `UNIQUE(user, external_pk_id)` при условии `external_pk_id != ''`
   - `UNIQUE(user, external_shikimori_id)` при условии `external_shikimori_id != ''`

   Пустые строки исключаются, иначе все ручные записи без внешних id конфликтуют между собой.

3. **Индексы** `(user, external_pk_id)` и `(user, external_shikimori_id)`. Сейчас
   `_find_existing` (`backend/media/views.py:963`) и `_annotate_existing`
   (`backend/media/views.py:704`) фильтруют по ним без индекса.

4. **Атомарный импорт.** `ImportView` оборачивает проверку+создание в `transaction.atomic()`
   и при `IntegrityError` от уникального ограничения перечитывает существующую запись и
   возвращает её (ветка `created: False`), как сейчас.

5. **Обработка конфликта в `MediaEntryViewSet.create/update`.** Так как внешние id принимает
   и `MediaEntryWriteSerializer`, создание/обновление с занятым id должно возвращать
   `409 Conflict` (или существующую запись), а не 500.

### Фаза 2 — продуктовое решение (перекрёстная идентичность, сценарий 2)

Два варианта на выбор:

- *Мягкий:* вернуть `external_imdb_id`/`external_tmdb_id` (удалены в
  `backend/media/migrations/0003_remove_mediaentry_external_imdb_id_and_more.py`) как
  дедуп-ключи и матчить по любому совпадению. «Уникальность по любому из N полей» одиночным
  `UniqueConstraint` не выражается — матч остаётся в коде, гонка для кросс-источника
  закрывается отдельной блокировкой.
- *Строгий:* дочерняя таблица `ExternalId(user, media_entry, source, value)` с
  `UNIQUE(user, source, value)`. Гонка внутри источника закрывается уникальностью, но
  слияние двух уже существующих записей требует отдельной логики.

### Фаза 3 — опционально

- scoped throttle для авторизованных на `/search/` и `/import/`: сейчас лимиты только у
  `AnonRateThrottle` (`backend/okid/settings.py:122-124`), а эти эндпоинты на каждый запрос
  ходят во внешние API и могут выжечь квоту ключей;
- пер-юзерные информеры: `Informer` глобальный и `unique`
  (`backend/media/models.py:27`), пользователи видят имена друг друга;
- дедуп файлов постеров (`poster_local`) по хэшу — экономия диска без смены модели.

## Подводные камни

- **Ограничения упадут на существующих дублях.** Пока в БД есть строки с одинаковым
  `(user, external_pk_id)`, `AddConstraint` завершится ошибкой. Чистка (шаг 1) обязательна
  и должна идти в той же миграции до добавления ограничений.
- **`IntegrityError` отравляет транзакцию.** Ловить его нужно во **вложенном** `atomic`
  (savepoint), иначе последующие запросы в том же HTTP-запросе упадут.
- **Условие частичного индекса.** Забыть `condition` → все пустые `external_*_id` начнут
  конфликтовать: ручное создание второй карточки без внешнего id сломается.
- **Разные источники не сходятся.** У картины из Шикимори заполнен только
  `external_shikimori_id`, у той же картины из ПоискКино — только `external_pk_id`;
  оба ограничения по отдельности не сработают. Это сценарий 2, он остаётся до Фазы 2.
- **`update` тоже может создать конфликт.** Если `update` проставит id, уже занятый другой
  записью пользователя, нужно обработать так же, как `create`.
- **Постеры дублируются по диску.** В B каждый пользователь хранит свой `poster_local` —
  одинаковые картинки лежат в `mediafiles` по разу на пользователя.

## Риски

- **Необратимость чистки (средний).** Слияние дублей удаляет строки; без полного бэкапа БД
  откат невозможен. Нужен снапшот и сухой прогон на копии.
- **Сценарии 2–4 остаются (средний).** Ограничения не ловят кросс-источник и ручное
  создание, пользователи продолжат получать часть дублей. Требуется явное продуктовое
  решение по Фазе 2/3.
- **Квота внешних API (средний).** Без auth-throttle рост числа пользователей упирается в
  лимиты PoiskKino/Shikimori и стоимость ключей.
- **Утечка имён информаторов (низкий).** Глобальный `Informer` делает имена рекомендаций
  видимыми всем пользователям.
- **Рост базы (низкий).** Пер-юзерные копии по определению дублируют метаданные и файлы;
  приемлемо, пока библиотеки небольшие.

## Открытые решения

1. Возвращать `external_imdb_id`/`external_tmdb_id` как ключи дедупа или ввести дочернюю
   `ExternalId`?
2. Блокировать ли ручное создание дублей по `title + year_start + media_type` введением
   нормализованного `dedup_key` (`UNIQUE(user, dedup_key)`) или только предупреждать?
3. Делать ли информеры пер-юзерными?
4. Добавлять ли auth-throttle для `search`/`import` в рамках этой работы или отдельно?

## Вне рамок

- Нормализация в общий `Media` + `UserMedia` (вариант A) — рассмотрена и отклонена.
- Изменение фронтенда: в варианте B API-контракт `/api/media/` не меняется.
